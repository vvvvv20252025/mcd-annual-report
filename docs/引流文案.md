**标题**：我用麦当劳官方 MCP 给自己写了一份年度报表

**正文**

```markdown
# 我用麦当劳官方 MCP 给自己写了一份年度报表

去年年底，我翻手机相册找一张截图，发现自己存了一整年的取餐小票，密密麻麻，日期从 1 月 3 日排到 12 月 31 日。我突然很想知道：这一年的我，到底点了些什么？

于是有了这个项目——**麦麦年度报告（McDonald's Wrapped）**：一个接入**麦当劳官方 MCP Server** 的 WorkBuddy Skill，把你一年的历史订单、餐品营养数据、积分账户与奖品记录，拉到本地，编译成一份九屏、可滚动、可截图分享的单文件 HTML 报告。

做这个项目的过程里，技术点比想象中有意思得多。这篇文章尽量把我踩过的坑和做的技术选择都写清楚，代码可以直接复制。

> 声明：本文项目为个人兴趣作品，非官方产品；文中所有数据均在用户本人授权下由官方 MCP 接口返回，本地处理。

## 一、为什么做「向后看」

在动手写代码之前，我先看了一眼现有生态里同类的 MCP 项目，几乎清一色是「向前看」的：

- 下一顿吃什么（推荐引擎）
- 怎么点更划算（优惠券计算器）
- 这一顿多少卡路里（热量计算器）

它们都是在解决「此刻」的问题。而我想要的是另一个方向：**回看已经发生过的一年**。

这两年「年度报告」这种内容形态被做透了——音乐平台有、地图有、聊天记录有。共同点是：它们都需要一批**已经存在的、只属于你的、带时间戳的数据**。而麦当劳官方 MCP Server 恰好开放了三类个人数据接口：**历史订单、餐品营养信息、积分账户**。这三样凑齐，「个人年度数据叙事」这件事第一次在餐饮场景里变得可做。

差异化也就清楚了：**别人都在给你建议下一顿，我给你写一份关于过去一年的总结。**

## 二、接入层：Streamable HTTP + Bearer Token

麦当劳 MCP Server 是远程托管的，地址是 `https://mcp.mcd.cn`，传输协议用的是 **Streamable HTTP**，鉴权靠请求头里的 `Authorization: Bearer <Token>`。

配置文件长这样：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer ${MCD_MCP_TOKEN}"
      }
    }
  }
}
```

注意 `Bearer` 后面那个 `${MCD_MCP_TOKEN}` 是**环境变量占位符**，不是字符串本身。绝大多数 MCP Client（WorkBuddy / Cursor / Cherry Studio / Trae / VSCode 都能）会在建立连接时用环境变量的值做替换。

这里有个细节值得说：`${...}` 这种写法看着像 shell 展开，实际是 MCP 客户端的配置约定。如果你的客户端不吃这一套，就老老实实写死：

```bash
export MCD_MCP_TOKEN="your-mcd-mcp-token"   # Linux / macOS
$env:MCD_MCP_TOKEN="your-mcd-mcp-token"      # Windows PowerShell
```

**Token 只走环境变量，不写进代码、不写进配置文件、不提交进仓库**——仓库里只提供脱敏后的 `mcp-config.example.json`。这条是底线，没有例外。

官方文档里两个错误码需要留意，接入前先记下来：

| code | 原因 | 处理 |
|:-----|-----|-----|
| 401 | Token 无效 / 过期 / 未提供 | 检查 `Authorization` 头与 Token 配置 |
| 429 | 触发限流（每个 Token 每分钟最多 600 次请求） | 降低调用频率，拉长间隔 |

600 次/分钟其实很宽松，但如果你的代码里有循环调用、或者重试策略写得激进，很容易踩到 429。我的做法是：**串行拉取 + 每类数据拉完立刻落盘缓存**，不要为了"并发更快"去并发打接口。

## 三、可复制的 JSON-RPC 调用示例

如果你不想装任何 SDK，用 `curl` 直接打 JSON-RPC 也能跑通全流程。Streamable HTTP 的完整握手顺序是：

**第 1 步：`initialize`**

```bash
curl -i -X POST https://mcp.mcd.cn \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer ${MCD_MCP_TOKEN}" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "initialize",
    "params": {
      "protocolVersion": "2025-06-18",
      "capabilities": {},
      "clientInfo": { "name": "mcd-annual-report", "version": "0.1.0" }
    }
  }'
```

**第 2 步：确认初始化通知**

从响应头里取出 `Mcp-Session-Id`，然后发一条 notification（没有 `id`）：

```bash
curl -X POST https://mcp.mcd.cn \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer ${MCD_MCP_TOKEN}" \
  -H "Mcp-Session-Id: <上一步返回的 session id>" \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
```

**第 3 步：列出工具 / 调用工具**

```bash
# 看服务端提供了哪些 tools
curl -X POST https://mcp.mcd.cn \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer ${MCD_MCP_TOKEN}" \
  -H "Mcp-Session-Id: <session id>" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'

# 真正拉数据：历史订单
curl -X POST https://mcp.mcd.cn \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "Authorization: Bearer ${MCD_MCP_TOKEN}" \
  -H "Mcp-Session-Id: <session id>" \
  -d '{
    "jsonrpc": "2.0",
    "id": 3,
    "method": "tools/call",
    "params": {
      "name": "order-list",
      "arguments": { "startDate": "2025-01-01", "endDate": "2025-12-31" }
    }
  }'
```

三个容易踩的点：

1. `Accept` 头必须同时带 `application/json` 和 `text/event-stream`，少了后者服务端会拒绝。
2. `Mcp-Session-Id` 是会话级的，后续每次调用都要带；它不跨进程复用，脚本每次跑都要重新 `initialize`。
3. `tools/call` 的返回体是 `content[].text` 里塞一段 JSON 字符串，**需要二次 `JSON.parse`**，别直接当对象用。

## 四、Python SDK 写法

真正写工程代码的时候还是 SDK 舒服。用官方 `mcp` 包，逻辑非常短：

```python
import asyncio, os, json
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

TOKEN = os.environ["MCD_MCP_TOKEN"]          # 只从环境变量读
BASE = "https://mcp.mcd.cn"

async def fetch(tool: str, args: dict) -> dict:
    async with streamablehttp_client(
        url=BASE,
        headers={"Authorization": f"Bearer {TOKEN}"},
    ) as (read, write, _):
        async with ClientSession(read, write) as session:
            await session.initialize()
            res = await session.call_tool(tool, args)
            # MCP 返回的 text 是字符串，需要再 parse 一次
            return json.loads(res.content[0].text)

async def main():
    orders = await fetch("order-list", {
        "startDate": "2025-01-01",
        "endDate": "2025-12-31",
    })
    print(f"拉到 {len(orders)} 条订单")

asyncio.run(main())
```

## 五、工具选型：为什么 `mall-order-list` 不能省

这是整个项目里最关键的一个技术决策。

官方 MCP Server 提供了 `order-list`（查询近期的**到店/外送**历史订单）和 `mall-order-list`（查询麦麦商城内**近一年**购买或兑换的商品订单）。第一反应是：`order-list` 不是已经够了吗？

不够。差在两个地方：

**第一，账要对得上。** 积分账户（`query-my-account`）和优惠券（`query-my-coupons`）是全量口径，但只靠 `order-list` 的话，商城里用积分兑换的实物、券类订单是不在里面的。你算出来的「今年赚了多少积分 vs 浪费了多少积分」会和账户显示的数字对不上——这种对不上的裂缝，比少几个数据点伤信任得多。加上 `mall-order-list` 之后，"消费—积分—兑换—奖品"这条链才能闭环。

**第二，时间跨度不一致。** `order-list` 是"近期"订单，`mall-order-list` 明确覆盖近一年。要做**年度**报告，光靠前者窗口不够；两者叠加才能拼出完整的 365 天。

于是我最终用了 6 个工具，各自对应报告里的一屏：

| Tool | 数据 | 落到哪一屏 |
|---|---|---|
| `order-list` | 历史订单（餐品/数量/时间戳/门店） | S1 第一单、S2 最爱 Top5、S3 消费曲线、S5 深夜画像 |
| `mall-order-list` | 近一年商城订单（积分兑换 / 实物） | S6 积分体检（与账户口径对齐） |
| `list-nutrition-foods` | 全量餐品官方营养数据 | S4 热量洞察（趣味换算） |
| `query-my-account` | 积分账户（可用/累计/过期） | S6 积分体检 |
| `query-my-coupons` | 优惠券列表与使用状态 | S6 辅助口径 |
| `query-my-prizes` | 积分抽奖奖品记录 | S7 程序员人格彩蛋 |

**热量这一屏必须用官方数据。** `list-nutrition-foods` 返回官方在售餐品的营养成分，我拿它返回的热量值做累加和换算，而不是自己维护一张"大概多少大卡"的近似值表——后者会随着新品上市立刻过期，也没法对账。换算我用的是"≈ 多少根红薯"（按一根约 238 kcal 折算），只做客观陈述和趣味换算，不做任何健康评判。

## 六、聚合：把一年的订单聚合成九屏

所有计算都在本地做，纯函数，无副作用，输入是订单数组，输出是一个 JSON：

```javascript
function computeReport(orders, points) {
  const byName = {}, monthly = new Array(12).fill(0);
  let kcal = 0, nightCount = 0, nightKcal = 0, nightSumMin = 0, first = null;

  orders.forEach(o => {
    const c = o.count ?? 1;
    byName[o.item] = (byName[o.item] || 0) + c;
    kcal += (NUTRITION[o.item]?.kcal || 0) * c;

    monthly[(o.month ?? 1) - 1] += c;

    // 深夜口径：22:00 - 06:00 算夜里
    const isNight = o.hour != null && (o.hour >= 22 || o.hour < 6);
    if (isNight) {
      nightCount += c;
      nightKcal += (NUTRITION[o.item]?.kcal || 0) * c;
      nightSumMin += o.hour * 60 + (o.min || 0);
    }
    if (!first || o.ts < first.ts) first = o;
  });

  const top5 = Object.entries(byName)
    .map(([name, count]) => ({ name, count }))
    .sort((a, b) => b.count - a.count)
    .slice(0, 5);

  const fmtHour = m => {
    m = Math.round(m);
    const h = Math.floor(m / 60) % 24, mm = m % 60;
    return `${h < 10 ? '0' : ''}${h}:${mm < 10 ? '0' : ''}${mm}`;
  };

  return {
    total: orders.length,
    first,
    top5,
    monthly,
    kcal,
    peakMonth: monthly.indexOf(Math.max(...monthly)) + 1,
    peak: Math.max(...monthly),
    lateNight: {
      count: nightCount,
      pct: Math.round(nightCount / orders.length * 100),
      avg: fmtHour(nightSumMin / nightCount),
    },
    points,
  };
}
```

几个设计上的取舍：

- **纯函数 + 无网络依赖。** 聚合层不碰 MCP，方便用固定样本写单测，也方便做"演示数据"模式。
- **深夜阈值固定在 22:00 / 6:00。** 这是个主观选择，我把它做成常量而不是散落在各处，改口径只改一处。
- **不做"健康建议"。** 热量只做换算和陈述。这既是产品边界，也是内容合规的底线。

最后一步是把结果 JSON 填进一个自包含的 HTML 模板，输出单文件：没有外链、没有 CDN 依赖、没有后端，双击就能在浏览器打开，手机上也能直接看。每一屏都按"值得被截图"的密度来设计——这是 Wrapped 式内容传播的前提。

## 七、隐私边界

这个项目处理的是**每个人的饮食记录**，隐私不是加分项，是准入门槛。我的边界是三条：

1. **Token 只走环境变量。** 仓库里只有 `${MCD_MCP_TOKEN}` 占位符，没有任何真实凭证。
2. **数据本地处理。** 拉取、聚合、渲染全部发生在用户自己的机器上，**不经过任何第三方服务器**，没有云端存储、没有埋点、没有上报。
3. **只读。** 项目用到的是查询类接口。我没有在报告生成流程里加任何下单动作——涉及支付与履约的接口，即使能用，也应该留给用户显式确认的场景，不该混在"生成报告"里。

## 八、结语

整个项目最让我满意的地方，是它证明了一件事：**当一个平台愿意开放个人数据接口，"回顾过去"这种需求，第一次可以被认真对待。**

从技术上讲，它是一次 Streamable HTTP + JSON-RPC 的标准接入、一个数据聚合函数、一个单文件 HTML 渲染；从产品上讲，它补上了一个没人做过的方向——不告诉你下一顿吃什么，而是认真讲完你过去这一年。

## 二、知乎（故事向 · 约 1500 字）

**标题**：我让 AI 把我的麦当劳订单史变成了一篇年终总结

**正文**

```markdown
# 我让 AI 把我的麦当劳订单史变成了一篇年终总结

一开始我只是想找一张截图。

去年十二月底，我帮朋友修一个线上问题修到凌晨，找手机相册翻那张白天的截图时，顺手划到了一整年的取餐小票照片——那是我某一趟出差随手拍的，那是一周连着三天的加班记录，那是一张一个人的薯条。

我盯着那一摞照片看了很久，突然冒出一个很朴素的念头：**我这一年，到底是怎么吃的？**

不是想算卡路里，也不是想省多少钱。就是想看看，这一年在我自己都没留意的地方，发生了什么。

## 起点是「点单记录里有生活痕迹」

我原本以为点单记录就是点单记录：餐品、金额、时间。但当我把它们按时间排开之后，我发现里面全是我自己都忘了的事。

三月那连续三周的晚上十一点半，都是同一个套餐，那段时间我正在赶一个上线；五月开始出现一个人在店里点的单人份，那几个月我搬了家；十一月突然密集出现一大份薯条和两杯饮料，那是项目上线前的那两周。

**数据没有讲故事，但数据把故事的轮廓照了出来。**

于是我决定做一个东西：把这一年的点单史，变成一篇像样的年终总结。

## 我做了什么

我用的是一个叫 WorkBuddy 的智能体，接上了**麦当劳官方 MCP Server**。简单说，官方把这个接口开放了出来，授权之后，AI 就可以通过标准化的方式读取你自己账号下的历史订单、餐品营养信息、积分账户和奖品记录。

然后我让它做了一件事：把这些数据，编译成一份九屏的、可以往下滑的、每一屏都值得截图的 HTML 报告。

出来的效果，比我预想的好很多。

第一屏是封面，写着你的昵称和你这年的第一单——我的是一月三号早上八点四十二分，一份猪柳蛋麦满分，时间早得像在赶一场不存在的早班。

然后是你最爱的五样东西。我的第一名是板烧鸡腿堡，全年二十三次。系统给它打上了一个标签叫「本命」，我不知道这个标签为什么让我有点感动，大概是因为它被统计得那么认真。

再往下是全年消费曲线，六月有一个明显的峰，二十三单。那是我最忙的一个月，也是我点得最凶的一个月。

然后是热量那一屏。数字很大，结尾换算成了「≈ 多少根红薯」。这个换算没有任何评价意味，纯粹是个单位转换游戏，但我看到那行字的时候还是笑出了声——它把我的严肃年度报告一下子变成了一件好玩的事。

**最扎心的是深夜那一屏。** 它告诉我，我这一年有 47 个订单下在晚上十点之后，深夜平均下单时刻是 **23:47**，最晚的一单在凌晨 02:14。

凌晨两点十四分。

我盯着这个数字看了很久。那不是一时冲动，那是一个持续了一整年的习惯。它告诉我，在这一年里，有多少次我并没有真的饿，只是需要一个理由把一天收个尾。

再往下是积分账户体检——今年拿了多少，兑换了多少，有多少因为忘了用而到期。这一屏是整份报告里最"有用"的一屏，因为它是唯一能直接转化成行动的。

最后两屏，一屏是给我颁了个程序员人格徽章，一屏是排版好的海报，可以直接截图发出去。

## 我为什么想把它做成开源

因为这件事不该只有我一个人看到。

说实话，市面上已经有不少基于点单数据的应用了，但它们几乎都在回答同一个方向的问题：下一顿吃什么、怎么点更划算、这一顿多少大卡。它们的注意力都在「往前看」和「往外看」。

我想做的是「往回看」。不是为了建议什么，纯粹是想把已经发生的一年，认真地讲完一遍。

而且这件事的技术门槛并不高——它是一次标准的 MCP 接入、一次本地数据聚合、一个单文件 HTML 渲染。真正花心思的是「讲什么」和「怎么讲」。

所以我把它开源了，MIT 协议，代码在下面这个地址：

**`https://github.com/vvvvv20252025/mcd-annual-report`**
（发布前请替换为实际仓库地址）

你只需要三步：

```bash
git clone https://github.com/vvvvv20252025/mcd-annual-report.git && cd mcd-annual-report
export MCD_MCP_TOKEN="your-mcd-mcp-token"     # 你的 MCP Token，只走环境变量
python -m mcd_annual_report --year 2025 --output mcd-annual-report.html
```

生成的是**一个 HTML 文件**，双击就能打开。所有数据在你的本地机器上完成拉取和计算，不经过任何第三方服务器。

## 四、V2EX（技术社区 · 约 400 字）

**标题**：[开源] 用麦当劳官方 MCP 生成的年度点单报告 Skill

**正文**

```markdown
做了个开源项目，写完自己都还挺喜欢的。

**做什么**：接麦当劳官方 MCP Server，把你一年的历史订单、餐品营养数据、积分账户、奖品记录拉下来，在本地聚合成一份九屏 Wrapped 式 HTML 年度报告。

**架构一句话**：授权 → MCP 拉数据（order-list / mall-order-list / list-nutrition-foods / query-my-account / query-my-coupons / query-my-prizes）→ 本地纯函数聚合 → 单文件 HTML 输出，无后端、无 CDN、双击即开。

**技术点**：
- Streamable HTTP 接入，`Authorization: Bearer <Token>`，Token 只走环境变量
- `mall-order-list` 不能省——否则商城兑换那部分对不上 `query-my-account` 的积分口径，账就平不了
- 热量用 `list-nutrition-foods` 的官方数据做换算，不自己维护近似值表
- 聚合层写成纯函数，好写单测，也好做 demo 模式
- 深色画布 + 每屏一色的 Wrapped 叙事排版，工程师审美版本

**为什么做这个方向**：现有的同类项目几乎都在「向前看」（下一顿吃什么、怎么省、算不算卡路里），做「向后看」个人数据叙事的几乎没有。官方开放了订单历史 + 营养 + 积分三类个人数据接口之后，这件事第一次可做。

代码 MIT 协议，README 里有可复制的 JSON-RPC 调用示例（initialize → notifications/initialized → tools/call），踩坑点都写了。

仓库：https://github.com/vvvvv20252025/mcd-annual-report
（发布前请替换为实际仓库地址）

求个 Star 🙏 这个比赛按 Star 数排名，也欢迎来提 Issue 讨论数据聚合的口径设计。

#WorkBuddy #1024程序员节
```
